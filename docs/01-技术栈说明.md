# 01 · 技术栈说明

> 面向使用者/维护者：本项目用了哪些技术、为什么这么选、各自负责什么。
> 代码在哪、怎么连，见 [`../ARCHITECTURE.md`](../ARCHITECTURE.md)。

## 总览

| 用途 | 选型 | 为什么 |
|---|---|---|
| 桌面外壳 / 原生能力 | Rust + Tauri 2 | 复用系统 WebView，复用系统 WebView；Rust 侧直接提供 IPC 命令 |
| 前端 | React 18 + TypeScript + Vite | 组件化 UI、严格类型；Vite 启动快，`tauri dev` 下热更新 |
| 前端 IPC 封装 | `src/api.ts` + `@tauri-apps/api` | 组件不直接 `invoke`，命令名 / 参数 / 返回类型集中在一处，便于测试与重构 |
| 契约测试 | Node.js `node:test` | 不启动应用即可校验配置、权限、CSP 与 IPC 三方一致 |
| Rust 测试 / 质量 | `cargo test` · `cargo clippy` · `cargo fmt` | Rust 侧行为测试与静态检查；`clippy -D warnings` 保证不积警告 |
| 打包 | Tauri CLI（本地 devDependency） | 生成 MSI / NSIS、DMG、deb / rpm / AppImage；无需全局安装 |

## 它是怎么跑起来的

1. `tauri dev` 先执行 `beforeDevCommand`（`npm run web:dev`）启动 Vite，再编译并启动 Rust 主进程。
2. Rust 主进程创建窗口，窗口加载 `devUrl`（开发）或打包进应用的 `frontendDist`（生产）。
3. 前端通过 `invoke` 调用 Rust 侧 `#[tauri::command]`；命令必须在 `lib.rs` 的 `generate_handler!` 注册。
4. 生产打包时 `beforeBuildCommand` 先构建前端到 `dist/web`，Tauri CLI 再把前端资源与 Rust 可执行文件打成安装包。

## 各组件职责

- `src/`：React UI。只负责展示与交互；所有原生调用经 `src/api.ts`。
- `src-tauri/src/commands.rs`：IPC 命令实现。调用原生对话框与文件服务；文件、路径、编码、索引逻辑在 library.rs。
- `src-tauri/src/lib.rs`：Tauri Builder 与命令注册；保持薄，不放业务逻辑。
- `src-tauri/capabilities/default.json`：窗口可用的 Tauri 权限。默认只有 `core:default`。
- `src-tauri/tauri.conf.json`：窗口、CSP、`identifier`、开发端口、打包与图标配置。
- `tests/contract.test.mjs`：配置与 IPC 契约的机械校验（配合 `sh manager.sh test`）。

## 配置与单一事实源

- **版本号**：只在 `src-tauri/Cargo.toml` 的 `version`；`tauri.conf.json` 省略 `version` 时会回退到它；前端经 `app_info` 命令读取。`package.json` 的 `version` 固定 `0.0.0`，不使用。
- **App 标识**：`src-tauri/tauri.conf.json` 的 `identifier`（反向域名，发布后不可改）。
- **开发端口**：只在 `build.devUrl`；`vite.config.ts` 从中读取并设 `strictPort`。
- **安全策略**：生产 CSP 在 `app.security.csp`，开发放宽只放 `devCsp`；窗口权限在 `capabilities/`。
- **命令**：统一走 `sh manager.sh <命令>`（`sh manager.sh help` 看全部），速览见 [`02-使用说明.md`](02-使用说明.md) §0。
